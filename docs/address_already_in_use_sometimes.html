Some more data points.

First. If we remove conn and the client entirely

import socket
from threading import Thread


with socket.socket() as sock1:
    sock1.bind(("127.0.0.1", 44444))
    sock1.listen()


with socket.socket() as sock2:
    sock2.bind(("127.0.0.1", 44444))

then it never errors on macOS. So sock2.bind() must have been clashing with conn, not sock1. (We know it wasn’t clashing with the client’s sock because the client’s local port isn’t 44444.)

Second. If we sleep(1) between the first and second with blocks, then it never errors. That suggests the clash is a matter of timing, not protocol.

Third. If we replace 127.0.0.1 by localhost, which adds a tiny name resolution delay before sock2 binds, then it only occasionally errors on macOS. (I got 3 errors in 10 runs.) That again suggests the clash is a matter of timing, not protocol, and that the timing is knife-edge.

Fourth. If we ensure conn is the active closer, rather than the client

import socket
from threading import Thread
from time import sleep


def client():
    sock = socket.create_connection(("127.0.0.1", 44444))
    sleep(1)
    sock.close()


with socket.socket() as sock1:
    sock1.bind(("127.0.0.1", 44444))
    sock1.listen()
    Thread(target=client).start()
    conn, _ = sock1.accept()
    conn.close()

with socket.socket() as sock2:
    sock2.bind(("127.0.0.1", 44444))

then it always errors on both.

But these errors have a different cause. The first error, on L20, is because sock2 is trying to bind to conn's address, but conn is still waiting for the client to close. The later errors, on L13, are because the active closer, conn, once the client has closed, is put in TIME_WAIT for a while, and the kernel blocks binds to addresses in TIME_WAIT. (The TIME_WAIT persists across runs.)

Where does that leave us? My main takeaway: conn.close() returns while the kernel is still closing the connection asynchronously, and the closing takes a fraction longer on macOS than Linux. Also, socket programming is delicate indeed.
